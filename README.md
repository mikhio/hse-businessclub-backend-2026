# QR-пропуск гостя

Тестовое задание на стажёра backend-разработчика Бизнес-клуба ВШЭ. Гость получает персональный QR в Telegram. Организатор отправляет боту фотографию QR, видит карточку и отмечает приход кнопкой. Начисление за приход сохраняется в журнале и выполняется один раз, в том числе при одновременной работе нескольких организаторов.

## Запуск

Нужны Docker Engine и Docker Compose. Python локально не нужен для контейнеров. Для вспомогательных команд настройки достаточно Python 3.12+.

1. Создать `.env` с независимыми случайными секретами, подставив числовой Telegram ID организатора:

   ```bash
   python3 -m scripts.configure --organizers 123456789
   ```

   Скрипт не перезаписывает существующий файл и не выводит секреты. Альтернатива — скопировать `.env.example` в `.env` и заменить три значения секретов. ID из примера вымышленный: его нужно заменить собственным.

2. В `.env` указать `BOT_TOKEN` отдельного тестового бота, полученный у BotFather. Токен не включать в исходники, README или историю Git. В `ORGANIZER_IDS` перечислить доверенные **числовые** Telegram ID через запятую.

3. Поднять всю систему одной командой:

   ```bash
   docker compose --profile telegram up --build -d
   ```

API доступен только на loopback: `http://127.0.0.1:18082`. Документация — `/docs`, проверка БД — `/health`. Данные PostgreSQL сохраняются в именованном volume при перезапуске. Команда `docker compose down` останавливает проект без удаления данных. Не использовать `down -v`, если данные нужны.

Если токена пока нет, для локального API и проверок достаточно `docker compose up --build -d`: профиль Telegram не запускается. Это не запуск живого бота. Добавив токен, выполнить команду из шага 3.

## Проверка в Telegram

1. Гость открывает личный чат с ботом и отправляет `/start` или `/qr`. Имя берётся из текущего Telegram-профиля отправителя, категория при саморегистрации — «Гость». Повторная команда сохраняет тот же пропуск.
2. Организатор из `ORGANIZER_IDS` отправляет фото этого QR, в том числе пересланное, или файл изображения. Бот самостоятельно скачивает и декодирует изображение. Можно отправить расшифрованный текст как резервный способ.
3. Бот показывает имя, категорию, баллы за текущее мероприятие и статус прихода. Кнопка «Отметить приход» начисляет `CHECKIN_POINTS`.
4. Повторный скан показывает отмеченный приход. Повторное нажатие старой кнопки сообщает, что приход уже отмечен; сумма и журнал не меняются.

Работа с пропусками разрешена только в личном чате. Групповые сообщения игнорируются. Недоверенный пользователь не может проверять чужие пропуска или вызывать кнопку организатора.

## Проверки

Полный набор unit- и PostgreSQL-интеграционных тестов в контейнере:

```bash
docker compose --profile test run --build --rm tests
```

Тесты создают случайную отдельную схему `test_qr_<uuid>` и удаляют только её. Они не очищают рабочие таблицы. Проверяются:

- подпись и подмена токена, другой ключ и другое мероприятие;
- реальное распознавание PNG, JPEG после сжатия и поворота, неверные изображения и несколько QR;
- основной HTTP-сценарий, журнал начисления и повторный чек-ин;
- запрет подделки `organizer_id`, подмены заголовка ID и чтения чужого QR;
- 16 одновременных чек-инов: ровно одно начисление;
- конкурентная регистрация: один гость и один пропуск;
- полный путь через настоящий aiogram `Dispatcher`: `/start` → выдача QR → скачивание JPEG → декодирование через backend → карточка → callback кнопки → повтор; подменён только сетевой транспорт Telegram;
- игнорирование групп и отказ обычному гостю с чужой кнопкой.

Для локального Python:

```bash
uv sync --locked
TEST_DATABASE_URL=postgresql+psycopg://user:password@localhost:5432/disposable_db uv run python -m pytest -q
uv run ruff check app scripts tests
```

Без `TEST_DATABASE_URL` PostgreSQL-тесты пропускаются; это не полная проверка. Офлайн проверка транспорта не подтверждает доставку в настоящий Telegram. Для неё нужны настоящий тестовый токен, два аккаунта и проход сценария выше.

Демонстрация работающего HTTP API без Telegram, с явно вымышленным гостем:

```bash
uv run python -m scripts.demo
```

## Архитектура и решения

```text
Telegram update
  → aiogram: отправитель, allowlist, загрузка фото, кнопка
  → HTTP API: scoped credentials, проверка действующего пользователя
  → GuestService: подпись, карточка, одноразовый чек-ин
  → PostgreSQL: guests + point_entries
```

`app/bot.py` отвечает за Telegram и HTTP-клиент; `app/api.py` — за транспорт API и валидацию; `app/service.py` — за бизнес-логику; `app/models.py` — за схему; `app/tokens.py` и `app/qr.py` — за пропуска и изображения.

У гостя хранятся UUID, Telegram ID, имя, категория, случайный `pass_id` и время регистрации. Подписанный QR содержит версию, идентификатор мероприятия и `pass_id`, но не имя или Telegram ID. Стабильная подпись HMAC-SHA256 строится из `PASS_SIGNING_KEY`; проверка выполняется через constant-time comparison. QR — предъявительский пропуск: фотография пригодна для повторного показа, поэтому её нельзя публиковать. Требование задания — не начислять повторно, а не сделать QR одноразовым. Для отзыва достаточно сменить `pass_id`; отдельный административный экран вне объёма задания.

Журнал содержит гостя, мероприятие, Telegram ID организатора, количество, код/описание причины и UTC-время. Сумма вычисляется из журнала. Ограничение БД `UNIQUE(guest_id, event_id, reason_code)` и `INSERT ... ON CONFLICT DO NOTHING RETURNING` не дают повторно начислить приход даже при гонке двух процессов. В таблице нет отдельного несогласованного счётчика баллов.

### Кто может вызвать API

HTTP API обслуживает доверенный бот; Telegram-пользователь не получает мастер-секрет `API_KEY`. Бот берёт ID из `message.from_user` / `callback.from_user`, а не из пересланного автора или пользовательского текста. Для каждого действующего ID вычисляется scoped credential `HMAC-SHA256(API_KEY, "telegram-actor:<id>")`. Он передаётся как `X-API-Key` вместе с `X-Telegram-ID`. API проверяет подпись и совпадение ID с телом/путём запроса, затем allowlist организаторов. Сам мастер-секрет не принимается как bearer credential. С credentials гостя нельзя подставить ID организатора или запросить QR другого гостя.

Мастер-секрет есть у доверенного процесса бота и backend. Его обладатель способен создавать credentials любого пользователя: это осознанная граница доверия, а не вход пользователя по знанию Telegram ID. При внешнем размещении бот и API должны обмениваться по приватной сети либо HTTPS; здесь API привязан к `127.0.0.1`, БД не публикует порт. Scoped credentials в логи не пишутся. Проверять их удобно через `scripts.demo`, а не вставлять секреты в URL.

Фото ограничено 8 МБ и 16 мегапикселями; учитывается EXIF-поворот. Декодер ZXing-C++ использует LocalAverage и GlobalHistogram: второй нужен для некоторых JPEG после компрессии. При нескольких различных QR обработка останавливается, чтобы не отметить случайного гостя. Распознавание не выполняется в event loop API, а идёт в worker thread синхронного обработчика.

### Допущения

- Один активный `EVENT_ID` на запуск. Баллы и приход считаются в его пределах; другой идентификатор позволяет новый чек-ин. В демо начисляется 10 баллов — это выбранное значение, а не правило клуба; оно меняется через `CHECKIN_POINTS`.
- Категория саморегистрации — «Гость». Поле хранится в БД отдельно; интерфейс импорта/управления категориями не требовался.
- Схема прототипа создаётся при старте через SQLAlchemy `create_all`. Для дальнейшей эволюции нужны версионированные миграции; `create_all` не мигрирует уже существующие колонки.
- Подпись привязана к мероприятию, но не имеет срока истечения. Новый `EVENT_ID` не принимает старые QR. Окончание/отзыв мероприятия управляются конфигурацией.
- Compose запускает один polling-процесс бота. API и БД отделены; Telegram-токен не нужен для запуска API.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `POSTGRES_PASSWORD` | Пароль локального PostgreSQL, не коммитится |
| `DATABASE_URL` | Строка подключения; Compose составляет её сам |
| `API_KEY` | Случайный мастер-секрет аутентификации бота и API, от 32 символов |
| `PASS_SIGNING_KEY` | Независимый случайный ключ подписи пропусков, от 32 символов |
| `BOT_TOKEN` | Токен отдельного тестового Telegram-бота |
| `ORGANIZER_IDS` | Доверенные числовые Telegram ID через запятую |
| `EVENT_ID` | Идентификатор активного мероприятия, 1–64 латинских символа/цифры/`_`/`-` |
| `CHECKIN_POINTS` | Баллы за приход, целое от 1 до 100000; по умолчанию 10 |
| `API_PORT` | Loopback-порт API на хосте; по умолчанию 18082 |
| `BACKEND_URL` | Адрес backend для бота; в Compose `http://api:8000` |
| `TEST_DATABASE_URL` | PostgreSQL для изолированных интеграционных тестов |

## Использование ИИ

Codex использовался для декомпозиции задания, реализации backend и Telegram-бота, подготовки тестов и проверки решения. Результат прошёл отдельное независимое ревью.

Конкретный пример проверки — распознавание JPEG: первый вариант декодера успешно читал PNG, но не проходил тесты со сжатым JPEG. Диагностика показала, что помогает второй алгоритм бинаризации; после его добавления тесты PNG, JPEG и поворота изображения прошли. Другие проверки покрывают подмену Telegram ID, доступ к чужому QR и конкурентное начисление баллов. Подробности — в [AI_ASSISTANCE.md](AI_ASSISTANCE.md).

Исходный код подготовлен для открытой сдачи после независимого ревью. Отправка в отбор выполняется отдельно. Живой Telegram-бот без предоставленного токена не запускался.
